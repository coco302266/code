#### D2：评估节点解析失败无日志

##### 问题

`assess_understanding_node` 的 except 分支返回  
`{resolved: False, hint_level: state["hint_level"], ...}`，  
与「模型正常判 false」**返回完全同形，且不打日志**。出问题时只能靠复现，  
换一个问题就得重新猜。

##### 方案（改 3 处，纯增量，不改任何行为）

**1. 文件头加 logger**

```python
import json
import logging
import os
```

并在 `get_llm` 之前加：

```python
logger = logging.getLogger(__name__)
```

**2. 把 try 收窄到只包解析，失败记 WARNING**

现在 `try` 从 `parse_assessment_result` 一路包到三个 return，  
异常面太大。改成先解析、再分支：

```python
    try:
        assessment = parse_assessment_result(response.content)
    except (json.JSONDecodeError, TypeError, ValidationError, ValueError) as exc:
        # LLM-6a：解析失败与「模型判 resolved=false」返回完全同形，
        # 不记日志的话线上永远无法区分这两者，只能靠复现。
        logger.warning(
            "评估节点解析失败，按「未掌握」降级处理 topic=%r in_hint_level=%d "
            "exc=%s: %s raw=%r",
            state["topic"],
            state["hint_level"],
            type(exc).__name__,
            exc,
            response.content[:500],
        )
        return {
            "resolved": False,
            "hint_level": state["hint_level"],
            "misconception": state["misconception"],
        }
```

要点：

- 捕获类型**一个不动**（保持现有行为），只加日志。
- `raw` 截断 500 字符，避免模型返回一大坨把日志刷爆。
- 记 `in_hint_level`，这样事后能看出"降级时停在第几层"。

**3. 成功路径补一条 DEBUG（可选但强烈建议）**

```python
    logger.debug(
        "评估节点解析成功 topic=%r resolved=%s model_hint=%d cur_hint=%d misconception=%r raw=%r",
        state["topic"], assessment.resolved, assessment.hint_level,
        state["hint_level"], assessment.misconception, response.content[:500],
    )
```

这条是给「模型说了什么 vs 代码解析成什么」分层看的。之前排查时靠临时脚本打原始返回，  
有了它以后不用再写脚本。DEBUG 级别，生产默认不出，需要时 `LOG_LEVEL=DEBUG` 打开。

**4.（可选，需 A 同意）让解析失败对外可见**

在 `TutorState` 加 `assess_degraded: NotRequired[bool]`，  
`app.py:512` 的 state 事件里带上 `degraded` 字段。  
好处：假 state（D1）与"真 state 但评估降级"两条异常路径可以统一用一个字段表达。  
代价：动 `state.py` + `app.py` + 前端，跨边界。**建议先不做，日志够了再说。**

#### D3：hint_level 棘轮效应

##### 问题

`graph.py:201`：

```python
"hint_level": max(state["hint_level"], assessment.hint_level),
```

只增不减，`resolved=true` 或换话题才归零。而模型在 `ASSESS_UNDERSTANDING_PROMPT`  
里**是知道当前 hint_level 的**（`hint_level=state["hint_level"]` 传进去了），  
所以它返回更低的值就是"这个学生有进步、可以少讲点"的信号 —— `max()` 把这个信号  
整段吞掉了。后果：resolved 漏判一次，学生永久卡在第 3 层，前端和 HTTP 状态码都看不出来。

##### 三个选项

| 选项             | 做法                                    | 优点                   | 缺点                                   |
| -------------- | ------------------------------------- | -------------------- | ------------------------------------ |
| **A（推荐）** 受控下调 | 模型值 < 当前值时，`next = max(cur-1, model)` | 响应速度信号，每轮最多降 1 级，不会抖 | 仍可能 3↔2 来回跳一次                        |
| B 完全信任模型       | 直接 `next = model`                     | 最简洁                  | temperature 0.4 下会明显抖动，学生看到的讲解深度忽深忽浅 |
| C 只观测不动        | 保持 `max()`，仅加日志告警                     | 零行为风险                | 不治本，学生照样卡死                           |

##### 推荐方案：A + C 的告警

```python
        model_hint = assessment.hint_level
        cur_hint = state["hint_level"]

        if model_hint >= cur_hint:
            next_hint = min(model_hint, 3)
        else:
            # 模型主动调低 = 学生有进步的信号。原来用 max() 把这个信号整段吞掉，
            # 后果是 resolved 漏判一次，学生就永久卡在第 3 层（只有换话题才归零）。
            # 这里允许下调，但每轮最多降 1 级：temperature 0.4 下模型会抖，
            # 一步到位地跟会让讲解深度来回跳。
            next_hint = max(cur_hint - 1, model_hint, 0)
            logger.info(
                "讲解深度下调 topic=%r %d -> %d（模型给 %d）misconception=%r",
                state["topic"], cur_hint, next_hint, model_hint,
                assessment.misconception,
            )

        # 已经讲到最深一层、模型又说不出学生具体哪里不懂 —— 这是 resolved 漏判的
        # 典型特征。不改行为，只留证据。
        if next_hint >= 3 and not assessment.misconception:
            logger.warning(
                "已到最深讲解层且模型未给出具体误解 topic=%r resolved=false "
                "—— 疑似 resolved 漏判，需人工核看", state["topic"],
            )

        return {
            "resolved": False,
            "hint_level": next_hint,
            "misconception": assessment.misconception,
        }
```

`min(model_hint, 3)` 是补一道上限：`AssessmentResult` 的 `Field(ge=0, le=3)` 已经挡过，  
这里是双保险，`HINT_STRATEGIES` 只有 0-3 四层，越界会 KeyError。

##### 为什么不需要改 prompt

模型已经拿到当前 hint_level 了，返回更低值本身就是判断结果。  
加 `progress: improved|same|worse` 字段能让信号更明确，但要改  
`AssessmentResult` + prompt + 所有 mock，收益不大。**留作后续。**

##### 配套测试（tests/test_graph.py 新增 3 条）

| 用例         | 输入                            | 期望                      |
| ---------- | ----------------------------- | ----------------------- |
| 步进下调       | cur=3, 模型=1                   | `hint_level == 2`（不是 1） |
| 升级路径不变（回归） | cur=1, 模型=2                   | `hint_level == 2`       |
| 最深且无误解告警   | cur=3, 模型=3, misconception="" | 产生 WARNING              |

##### 现有测试是否受影响

查过了：`tests/test_graph.py` 里**没有**"模型值低于当前值"的用例，

#### 3. 不合理之处（按严重度排序）

##### 3.1 【最严重】无重排 —— 而数据证明答案就在这里

D5 基线实测：**库内题 top3 命中 6/7，top1 命中仅 4/7**。

把这个差异拆开看，指向非常明确：

| 现象                       | 含义                     | 病灶       |
| ------------------------ | ---------------------- | -------- |
| 6/7 在 top3 内             | **召回没问题**，正确切片已经被取回来了  | —        |
| 其中 2/7 排在 top1 之外        | **排序有问题**，它排在某个不相关切片后面 | 缺重排      |
| 1/7 完全未命中（HTTPS vs HTTP） | 召回失败                   | 文档结构（D8） |

**dense 检索是双塔结构**（query 和 doc 各自独立编码），它擅长"把相关的捞回来"，不擅长"把最相关的排最前"。业界共识是：**召回交给双塔，排序交给交叉编码器**。我们现在只有前半截。

这一条的价值在于：**不需要动 embedding、不需要换向量库、不需要动文档**，只加一个重排环节，就能直接改善 2/7 的 top1 错误。

##### 3.2 已有的知识信号被丢弃

`agent/graph.py` 的 `extract_topic_node` 每轮**花一次 LLM 调用**抽出知识点名称（如"死锁"），写进 state。然后——

- 检索用的是**原始 message**，不是这个 topic
- `category`（操作系统 / 计算机网络）已经写进 metadata，但检索时完全不过滤

即：花的这次 LLM 调用只服务了状态机，**对检索零贡献**。而且提问"那怎么预防呢？"这类追问（在状态机里是常态）本身不含检索所需的关键词，用原文检索是次优的——用已抽出的 topic 会稳得多。

##### 3.3 两路结果无融合排序

PDF 上下文（k=5）恒定排在 KB 上下文（k=4）之前，纯粹因为拼接顺序。若学生传了一份与当前问题无关的 PDF，这 5 个切片会稳定挤占 prompt 前部，而模型对**前部内容的注意力更高**。这不是"检索不准"，是"上下文组装策略缺失"。

##### 3.4 无质量闭环

`smoke_rag.py` 是离线手工脚本，9 道固定用例。改切分、改 k、加文档之后，没有任何机制阻止质量回退。同理，线上也没有检索命中率、无召回率的观测。

#### 4. 候选方案

##### 方案 1：重排（Rerank / Cross-Encoder）★ 重点

在 dense 粗召回之后加一个交叉编码器，对 (query, doc) 逐对打分重排。

**实测的关键事实：本项目零新依赖。** `fastembed` 已在 `requirements.txt` 中，且 0.9.0 自带 `TextCrossEncoder`：

```
BAAI/bge-reranker-v2-m3-int8              0.57 GB   ← 多语言，量化，性价比最高
BAAI/bge-reranker-base                    1.04 GB
jinaai/jina-reranker-v2-base-multilingual 1.11 GB
```

| 维度   | 评估                                      |
| ---- | --------------------------------------- |
| 解决问题 | 3.1 的 top1 排序错误（2/7）                    |
| 新增依赖 | **无**                                   |
| 新增模型 | 0.57 GB（本地 CPU 推理，一次性下载）                |
| 延迟成本 | CPU 上对 10 个候选打分约 100-300 ms（需实测）        |
| 代码侵入 | **仅 `retriever.py`**，约 30 行，不动 `app.py` |
| 回退成本 | 极低（一个开关）                                |

**配套修正我此前的建议**：昨天我说"k 从 4 提到 6"——**引入重排后这个说法要改**。正确策略是**放大粗召回**（k=10~~12）+ 重排取 top 3~~4。因为重排负责纠错，粗召回阶段就应该宁可多捞；只有 4 个候选时重排没有腾挪空间。修正后的链路：

```
similarity_search(k=12)  →  TextCrossEncoder 打分  →  取 top 4  →  注入
```

##### 方案 2：元数据过滤 / 复用 topic

利用已有的 metadata 和已抽出的 topic，收窄检索范围。

| 维度   | 评估                                                                         |
| ---- | -------------------------------------------------------------------------- |
| 解决问题 | 3.2；跨学科误召回（问死锁却召回 TCP 切片）                                                  |
| 两种做法 | ① `where={"category": "操作系统"}` 硬过滤；② 把 topic 拼进查询文本（`"{topic}：{message}"`） |
| 新增依赖 | 无                                                                          |
| 代码侵入 | 小；但**做法② 要动 `app.py` 的调用处**（需把 topic 传进检索函数）                               |
| 风险   | 硬过滤有"过滤错就完全召回不到"的隐患，建议先上做法②                                                |

##### 方案 3：混合检索（Dense + BM25 + RRF）

| 维度      | 评估                                                                            |
| ------- | ----------------------------------------------------------------------------- |
| 解决问题    | 专有名词/缩写检索（"LRU""TLB""NAT"这类 dense 不敏感的词）                                      |
| 新增依赖    | `rank_bm25`（langchain-community 里 `BM25Retriever` 已可 import）                  |
| **中文坑** | ❗ **BM25 默认按空格分词，中文整句会被当成一个 token，效果几乎为零**。中文必须先分词（jieba），而 `jieba` 当前**未安装** |
| 结论      | 收益真实但引入两处新依赖 + 一个中文特有的调试面，**优先级低于方案 1**                                       |

##### 方案 4：查询改写 / 多查询（Multi-Query、HyDE）

| 维度 | 评估                                                                     |
| -- | ---------------------------------------------------------------------- |
| 做法 | 用 LLM 把问题改写成 2-3 个变体，各检索一次后合并                                          |
| 成本 | **每次检索多 1 次 LLM 调用**，首字延迟明显上升                                          |
| 结论 | 对当前场景**过重**。且 `extract_topic_node` 已经在做类似的事，优先把它的产出用起来（方案 2），而不是再加一次调用 |

##### 方案 5：父子检索（Parent-Child / Small-to-Big）

小块检索、大块返回：用小块做精确匹配，命中后把所属的整个小节交给 LLM。

| 维度   | 评估                                                                 |
| ---- | ------------------------------------------------------------------ |
| 解决问题 | 同时解"检索精度"和"上下文完整"，是 D8（切分粒度）的更优解                                   |
| 实现   | LangChain `ParentDocumentRetriever`，或 Chroma 双 collection 自建       |
| 代码侵入 | **中**；检索层要从裸 `similarity_search` 换成 retriever 对象，牵扯 `app.py` 的调用方式 |
| 结论   | 架构上更正统，但应在方案 1 之后评估（方案 1 见效更快）                                     |

##### 方案 6：自反思检索（Self-RAG / CRAG）

检索后让 LLM 自评"这些资料是否相关"，不相关则改写查询重检。

| 维度 | 评估                                        |
| -- | ----------------------------------------- |
| 成本 | 每次检索多 1-2 次 LLM 调用 + 1 次检索                |
| 结论 | **当前规模下不推荐**。限流 10 req/min、单机演示场景，收益不抵复杂度 |

## 3、原名 PROPOSAL_RAG_EVAL_DATASET.md

### 检索评测集扩充方案

结论先行：**没有一个能直接下载的「本库评测集」**，原因不是没找到，而是评测集的定义决定的（见第 1 节）。但可下载的资源有确定用途，本库自身还藏着一批零成本的高质量题。本轮已把评测集从 **40 条扩到 75 条**，其中 35 条不需要任何标注。

---

#### 1. 为什么「直接下载一套数据集」这条路走不通

评测集是 `(query, expected)` 的集合，而本项目里 `expected` 必须是**本库 8 篇文档的 topic 之一**（判定逻辑见 `smoke_rag.py:top_hit`，归一化后做子串包含匹配）。

公开的中文检索数据集（T2Retrieval、DuReader Retrieval、MIRACL-zh、CmedqaRetrieval 等）都带 qrels，但那些标注指向**它自己的语料库**——新闻、百科、网页。下载下来只有 query 侧能用，label 全部作废。换句话说，能借的是「别人怎么问」，借不到「问了该命中本库哪一片」。

这还叠加了一个网络事实：

| 源 | 实测结果（2026-10-19 本机） |
|---|---|
| huggingface.co 直连 | ✗ 8s 超时（000） |
| hf-mirror.com | ✗ 8s 超时（000） |
| api.github.com | ✗ 15s 超时 |
| **raw.githubusercontent.com** | **✓ 200，1.5s** |
| gh-proxy.com（镜像） | ✓ 200，7s（慢一倍，作 fallback） |

C-MTEB 系列全在 HF 上，本机拿不到。所以标准 benchmark 这条路当前是断的——即便以后通了，它们也只能用于「换一套语料横向比较检索器」，不能当本项目的回归门禁。

---

#### 2. 三个源的实测：能下什么、值多少

我把能直连的题库逐个下下来看了标题形态，结论差别很大：

| 来源 | 是否可下 | 内容形态 | 标签可用性 |
|---|---|---|---|
| **本库 `## 面试常问`** | 本地，零下载 | 天然问句（"为什么需要 CA？"） | **✓ 归属文档即答案** |
| JavaGuide（GitHub raw） | ✓ 7 文件 ≈250KB | 标题即问句，OS/计网高度对口 | ✗ 需推断 |
| CS-Notes（GitHub raw） | ✓ 5 文件 ≈92KB | 二级标题是名词性章节名（"二、HTTP 方法"） | ✗ 且非问句形态 |

CS-Notes 的实际形态让我放弃了它作为问句源：

```
## 二、HTTP 方法
## 4XX 客户端错误
## 几、破坏互斥条件
```

这些是笔记的章节编号，不是提问方式，学生不会这么问。收进候选池只是噪音（实测第一版 202 条 weak 层里，绝大多数是这类碎片）。

真正对口的是 JavaGuide——它的三级标题基本都是问句：

```
### 产生死锁的四个必要条件是什么？
### HTTP 和 HTTPS 有什么区别？（重要）
### 为什么 DNS 用 UDP？
```

#### 3. 最关键的一条：最好的题源在自己库里

`knowledge/cs/` 的 8 篇文档，每篇都有一个 `## 面试常问` 小节，里面是 4~5 条真实面试问句。**这些问句的归属文档就是正确答案**，标签零成本、100% 可信。

之前的 40 条评测集一条都没用上它们。本轮把 35 条全部抽出并入正式集（`kind: kb-interview`，8 个 topic 每类 4~5 条，覆盖均匀）。

这不是把「已有答案的题」凑数——它测的是一个之前没测过的维度：**同一片资料里长出来的问句，检索能不能稳定把它排到第一**。实测结果（见第 6 节）是 33/35，**并没有全绿**，失败的 2 条恰好暴露了知识库的归属边界问题。

#### 4. 分层设计：自动化的边界划在哪

`build_eval_cases.py --gen` 把候选分成五层，层与层的区别只有一个：**这条的标签是怎么来的**。

| 层 | 来源 | 标签来源 | 能否自动进正式集 |
|---|---|---|---|
| `core` | 本库面试常问 | 问句所在文档的标题 | **✓ 可以**（`--merge-core`） |
| `auto` | 外部题库 + 问句 | 自动判定 + 命中本 topic 专属词 | ✗ 必须人审 |
| `weak` | 外部题库 + 问句 | 自动判定，但只命中跨篇通用词 | ✗ 判错率最高，优先审 |
| `oos` | 外部题库 | 未命中任何 topic | 观察用，不当门禁 |
| `review` | 外部题库 | 名词性标题，非问句形态 | 默认不收（`--include-terms` 才收） |

**为什么 `auto` 层不能自动合并**：自动标签的判据是「问句里的词和知识文档里的词重合」，而检索链路本身也吃词重合（BM25 那一路尤其明显）。用这种题做门禁，等于用同一套信号既出题又判卷——分数会虚高，且永远发现不了「语义对但用词不同」的失败。

##### 自动判定的做法与踩过的坑

- 特征词不手写，从知识文档自动抽 `(词数/本篇总词数) × log(1+篇数/df)` 的 top 40。手写词表的话，知识库一扩就得跟着改，改漏了判定会静默变差。
- **必须用归一化词频**。第一版用原始计数，`tcp-vs-udp.md` 里提了几次 HTTP（讲 HTTP Keep-Alive），"HTTP" 就成了那篇的高分特征词，「HTTP 和 HTTPS 有什么区别？」被判成 TCP 与 UDP——这是致命错误，因为它正好是核心用例。
- **词频门槛抬到 3**。出现 2 次的往往只是顺带一提：`http-https.md` 提过 WebSocket，于是「什么是 WebSocket」被判成 HTTPS 主题。
- **`strong` 判据取代分数阈值**。分数绝对值不好解释也不好定阈值（实测中位 0.0236、P75 0.0538，但判对判错的分数是重叠的）。改成看「命中的词里有没有只在这一篇出现的」——「死锁」只在 deadlock.md 出现，命中它就是硬证据；「进程」横跨三四篇，命中它说明不了什么。这个判据人也能一眼复核。

---

#### 5. 自动映射的真实准确率：约 2/3，所以必须人审

我把最终 `auto` 层 22 条逐条核了一遍：

| 判定 | 条数 | 例子 |
|---|---|---|
| 可用 | 15 | 「产生死锁的四个必要条件是什么？」→ 死锁 |
| 边缘可接受 | 1 | 「物理层主要做啥？」→ 分层模型（库内有分层但不细讲物理层） |
| **topic 判错** | 3 | 「mmap、COW 和共享内存有什么关系？」→ 判进程与线程，应为虚拟内存 |
| **其实是库外** | 3 | 「SSE 与 WebSocket 有什么区别？」→ 判 HTTPS，库内根本没讲 |

**约 68% 可直接用**。这个数字是全篇最重要的：它说明自动化的作用是省「从零想题」的成本，**不是省「审核」的成本**。审核只需要回答一个问题——这条题正常人会认为答案在那篇文档里吗？有 `evidence` 字段（命中的词）在，判断很快。

顺带一个副产品：那 3 条「判成 HTTPS 其实是库外」的题（WebSocket / SSE），是**比 Redis 好得多的负例**。Redis 与 OS/计网向量距离远，任何检索器都不会误召回；而 WebSocket 和 HTTP 语义极近，如果检索器把它硬塞给 `http-https.md`，那就是真问题。这才是负例该有的难度。

## 5、原名 PROPOSAL_RAG_SCALE.md

### 检索层面向扩库的设计

> **作者**：B（Prompt / RAG）  
> **范围**：`agent/rag/`、`knowledge/`、`build_kb.py`  
> **状态**：待审核（第 8 节有待勾选决策点）  
> **前提**：知识库将从 66 片扩到数百片以上  
> **核验方式**：全部数字为本地实跑，非估算；方法局限见 2.4

---

#### 1. 结论摘要

三句话：

1. 扩库后第一个断的不是向量检索，是**重排吞吐**——0.19~0.25s/条且严格线性。
2. **加大粗召回条数没有收益**：366 片下 6/12/24 条候选的 top1 完全相同（都是 6/7），只是把延迟从 2.0s 抬到 6.8s。
3. 所以扩展方向是「**缩小进入候选池的干扰**」，不是「扩大候选池」。参考实现走三级：元数据预过滤 → 文档路由 → 父子检索。

一句话设计原则：**给重排的候选条数必须是与库规模无关的常数（10~16 条）**。做到这一点，库扩到几千片，检索延迟也基本不变。

---

#### 2. 实测

##### 2.1 重排成本随候选条数线性增长

`BAAI/bge-reranker-v2-m3-int8`，本机 CPU，单 query，取两次最快：

| 候选条数 | 4       | 6       | 10      | 20      | 30      | 50      |
| ---- | ------- | ------- | ------- | ------- | ------- | ------- |
| 耗时   | 0.89s   | 1.14s   | 2.04s   | 4.82s   | 7.63s   | 12.69s  |
| 折算   | 223ms/条 | 189ms/条 | 204ms/条 | 241ms/条 | 254ms/条 | 254ms/条 |

这条曲线决定了扩展的天花板：候选池放到 30 条，单次检索就 7.6s，叠加评估图的 LLM 调用后首 token 会突破 25s。**候选数必须被预算约束住。**

##### 2.2 扩库后加大候选数没有收益

临时灌入干扰切片模拟扩库（构造方式见 2.4），跑同一套 7 道题：

| 库规模   | k=6                 | k=12            | k=24            |
| ----- | ------------------- | --------------- | --------------- |
| 66 片  | top1 **7/7**（2.15s） | top1 7/7（3.90s） | top1 7/7（6.93s） |
| 166 片 | top1 **6/7**（1.98s） | top1 6/7（3.81s） | top1 6/7（6.86s） |
| 366 片 | top1 **6/7**（2.02s） | top1 6/7（3.84s） | top1 6/7（6.84s） |

top4 命中在**所有**组合下都是 7/7。

两个结论：

- **top1 的损失不是召回不足**。若正确切片没被召回，加大 k 会把它捞回来；实测 k 从 6 加到 24 一名都不变，说明它一直在候选池里，只是重排把它排到了后面。
- **final_k=4 目前仍有缓冲**。正确切片始终落在注入的 4 片内。

##### 2.3 掉分只出现在跨知识点题

366 片、k=6 的逐题明细：

```
O 死锁产生的四个必要条件是什么？   ['死锁','死锁','干扰文档-9','干扰文档-35']
O TCP 为什么需要三次握手…        ['TCP 三次握手…' ×4]
O 进程和线程有什么区别？          ['进程与线程' ×4]
O HTTPS 和 HTTP 有什么不同？      ['HTTPS…','HTTPS…','TCP/IP 分层…','TCP/IP 分层…']
O TCP 和 UDP 该怎么选？          ['TCP 与 UDP','TCP/IP 分层…','TCP 与 UDP','TCP 与 UDP']
O 页面置换 LRU 是怎么工作的？      ['虚拟内存与页面置换' ×3,'干扰文档-12']
. 死锁和进程调度算法有关系吗？      ['干扰文档-12','死锁','死锁','进程调度算法']
```

6 道单知识点题 top1 全部守住；唯一掉的是同时跨「死锁 + 进程调度」的那道——干扰切片抢了第 1 名，正确切片退到第 2、3 位，仍然注入成功。

**所以扩库后的质量风险集中在「一句话涉及多个知识点」的场景，而不是普通单点提问。**

##### 2.4 本组实验的方法局限（必须一起看）

- 干扰切片取自仓库根目录 `docs/tutorial.md`（项目源码课程，同属技术文本但不在 OS/网络八股范围），按知识库同样的 500/80 参数切分后循环填充。**同一切片最多重复 3 次**，会高估「同一内容挤占多个名次」的程度。
- 真实扩库是「新增不同的知识点文档」，干扰更分散，但语义距离更近（同在 OS/网络域内）。两种效应方向相反，所以 166→366 片都停在 6/7 不能直接外推为「扩到 366 片只掉一题」。
- 因此本文只用它支撑**方向性结论**（加大 k 无收益、掉分发生在排序而非召回），不用它预测扩库后的绝对分数。

#### 4. 设计：三级缩放

##### 4.1 总原则：候选池预算

把「送进重排的条数」当作固定预算来管理，不随库规模增长：

```
候选池预算 C = 10~16 条（重排 2~4s，仍在可接受区间）
```

库变大时，减少的是「进入预算池的干扰」，而不是增加预算。三级方案就是三种缩池手段，越往后越精细、越贵。

##### 4.2 L0 结构层（现在就该有，行为不变）

不改变任何检索行为，只把「将来的变数」从散落的常量变成集中的可调项：

| 改动       | 做什么                                                                                             | 66 片下的表现       |
| -------- | ----------------------------------------------------------------------------------------------- | -------------- |
| 参数集中     | `COARSE_K` / `FINAL_K` / `RERANK_BATCH` 收进一个 `RetrievalConfig`，加 `coarse_k_for(n_chunks)` 自适应函数 | 函数返回 6，与现在完全一致 |
| 检索 trace | 每轮记录「候选数 / 重排耗时 / 是否降级 / 是否走了过滤」，先只打 DEBUG 日志                                                   | 零影响，但扩库时能立刻定位  |
| 评测集外置    | `CASES` 从代码里挪到 `rag_eval_cases.json`，支持按库规模跑同一套                                                 | 题目数量可扩充，代码不用动  |

##### 4.3 L1 文档路由（文档数 > 15 篇 或 切片数 > 150 时启用）

**做的事**：两阶段检索——先选文档，再选切片。

```
学生问题 ──①──> 文档索引（每篇 1 条，共 30~50 条）
                    │ 取 top-3 篇
                    ▼
              ②──> 主库 chunk 检索，filter={"source": {"$in": [3 篇]}}
                    │ 候选池 3 篇 × 8 片 ≈ 24 片
                    ▼
              ③──> 现有链路（BM25 + RRF + 重排取 4）
```

- **文档索引怎么建**：不调 LLM、不用人工。`build_kb.py` 里为每篇文档生成一条 Document，内容是「一级标题 + 全部二级标题 + 首段」。这就是一份天然的结构化摘要。
- **成本**：多一次 30~50 条规模的小集合检索，毫秒级；主库候选池从「全库竞争」缩成「3 篇内竞争」。
- **失败退化**：过滤后召回为空 → 自动回退全库检索（与现在行为一致），不抛错。
- **为什么不直接按 `category` 过滤**：`category` 只有 4 个值，OS 一类就占一半切片，粒度太粗；而且分错类别会导致完全检索不到，比现在的「召回到无关内容」更糟。`category` 过滤只作为路由失败的二级兜底。

##### 4.4 L2 父子检索（切片数 > 500 或 D8 黑洞复现时启用）

**做的事**：用小块检索、返回大块。

- 建索引时切成两层：child 约 200 字（用于检索，向量更聚焦），parent 是对应的二级小节全文（用于注入，约 600~900 字）。
- 命中 child 后按 `parent_id` 聚合去重，返回 parent 文本。
- 两个收益：① 解决 D8「综合型 chunk 成为万金油」——小块让每个向量只表达一件事；② 扩库后切分粒度不必再迁就注入长度。
- 代价：索引条数约 ×2.5；parent 变长后 `final_k` 要相应降到 3 左右控制注入量。

##### 4.5 配套：重排吞吐（已落地）

本机无 GPU，批处理是负收益。实测（候选 6/12/18/30 条一致）：

| 6 条  | **0.73s** | 0.90s   | 1.52s   | —        |
| 12 条 | **2.18s** | 2.62s   | 3.04s   | —        |

## 6、原名 PROPOSAL_SCOPE_PREFILTER.md

### 单库 + `scope` 元数据 + 检索前 pre-filter：设计与改动评估

> 2026-10-26 ｜ 状态：**设计完成，未实施**（等触发条件）
> **修订（12:10）**：补入规模实测（§九）。结论由"全塞一个 collection"修正为
> **两库分层**——共享库仍独立且**不加过滤**，`scope` 过滤只用于课堂池。
> 依据：Chroma 带 `where` 的检索耗时随过滤子集大小线性增长（§9.3），全库方案会把共享库拖慢 50 倍。
> 结论先行：**改动属于"中等"，约 180 行改动 + 60 行新脚本 + 35~45 例单测；但当前规模不该做。**
> 该方案的真正成本不是"写多少代码"，而是引入一个**不报错的静默泄漏面**（漏传 filter 就跨课堂泄漏），
> 以及**课堂语料会通过 BM25 的 IDF 反过来影响共享库的排序**——这是单库方案的固有耦合，
> 多 collection 方案没有这个问题。

---

#### 一、目标与边界

**要解决什么**：把「共享库 / 课堂库 / 会话库」三层资料放进**一个 Chroma collection**，
靠元数据 `scope` 区分归属，检索时用 `where` 做**检索前过滤（pre-filter）**，
从而避免 collection 数量随课堂数线性增长。

**不解决什么**：不改变"写入要分层、审核才晋升"的内容治理口径；
不改变 `/chat` 的请求协议；不改变金标准与评测口径。

---

#### 二、数据模型设计

##### 2.1 `scope` 取值

| scope 值 | 含义 | 写入方 | 可见范围 |
|---|---|---|---|
| `shared` | 共享教材库（`knowledge/cs/*.md`） | `build_kb.py` / `update_kb.py` | 所有人 |
| `classroom:<id>` | 课堂资料 | 教师上传（方案 B） | 该课堂成员 |
| `session:<sid>` | 会话级上传件 | `/upload`、`/upload/teacher` | 仅本次会话 |

**不要用 `classroom_1` 这种下划线拼接**：`classroom:1` 带冒号是有意的——
冒号在文件名/路径里不常见，后续若要把 `scope` 直接映射到目录名不会与 `_` 分隔的
复合名混淆；且解析 `scope.split(":", 1)` 比正则可靠。

##### 2.2 元数据 schema（在现有字段上新增 3 个）

```python
{
    # —— 现有字段（不变）——
    "subject": "cs",
    "category": "os",
    "topic": "死锁的必要条件",
    "source": "os/deadlock.md",          # 相对 knowledge/cs 的路径
    "doc_hash": "a1b2c3d4e5f6a7b8",      # 源文件 sha256 前 16 位
    "chunk_params_hash": "…",            # 切片参数快照
    # 父子模式才有：
    "parent_id": "os/deadlock.md#2",
    "parent_text": "…",
    "parent_title": "…",
    "parent_start": 1200,

    # —— 新增（scoped 版）——
    "scope": "shared",                   # 检索过滤的唯一依据
    "scope_kind": "shared",              # shared | classroom | session（冗余但便于统计）
    "owner_id": 0,                       # 课堂/会话的归属 id；shared 记 0
}
```

`scope_kind` 是冗余字段，为的是让「按类型统计」（如"课堂资料一共多少片"）不必解析字符串。

##### 2.3 唯一性：`source` 必须带 scope 前缀，否则 `parent_id` 会撞

现状 `parent_id = f"{source}#{idx}"`（`indexer.py:195`），`source` 是相对路径。
两个课堂各传一份 `讲义.md` → 两边 `source`、`parent_id` 完全相同 →
**父子聚合会把 A 课堂的 parent 当成 B 课堂的重复项丢掉**，且 `_dedupe(("source","start_index"))`
也会把它们当同一条。这是单库方案最隐蔽的正确性陷阱。

**做法**：课堂/会话资料的 `source` 前缀化（`classroom:7/讲义.md`），共享库 `source` **保持原样**
（这一点很关键，见 §五：`source` 参与指纹）。

#### 三、检索设计

##### 3.1 过滤点：必须在 ANN 阶段，不能检索后再筛

Chroma 1.5.9 实测（`langchain_chroma` 的 `filter=` 直通 `query(where=...)`，`vectorstores.py:780`）：

| 探针 | 结果 |
|---|---|
| 无过滤，查询向量与 `classroom_2` 某片完全一致 | top1 = 那一片（**证明不过滤就跨课堂召回**） |
| `where={"scope":{"$in":["shared","classroom:1"]}}` | 返回 5 条，`classroom:2` **被排除** |
| `where={"scope":"classroom:1"}` | 只返回该课堂 2 条 |
| `$and`：`scope $in` + `source $in` | 正常（2 条） |
| 元数据**没有** `scope` 的旧切片 | 带过滤时**被排除**（故迁移必须回填） |

结论：`where` 是 ANN 前的子集过滤，**不会出现"先召回 6 条再筛掉一半"的信息损失**。

##### 3.2 签名改动

```python
def retrieve_knowledge_docs(
    vectorstore: Chroma,
    query: str,
    k: int | None = None,
    topic: str = "",
    trace: dict | None = None,
    scopes: list[str] | None = None,      # 新增：None = 不过滤（兼容现状）
) -> list[Document]:
```

内部：

```python
def _scope_where(scopes: list[str] | None) -> dict | None:
    """纯函数：把 scope 列表翻成 Chroma where。空/None → None（不过滤）。"""
    if not scopes:
        return None
    if len(scopes) == 1:
        return {"scope": scopes[0]}
    return {"scope": {"$in": list(scopes)}}
```

然后 `vectorstore.similarity_search(search_query, k=coarse_k, filter=_scope_where(scopes))`。

`scopes=None` 时行为与现在**完全一致**——这是零回归的兼容开关，也是分阶段上线的抓手。

##### 3.3 BM25 怎么办（这是全案最容易做错的一处）

`_bm25_search`（`retriever.py:422`）现在是**全局打分后取 top-k**，没有任何过滤。
两个错误做法：

- ❌ **按 scope 各建一份 BM25**：IDF 在不同语料里不可比，小课堂语料的 IDF 噪声极大；
  而且缓存键要从 1 个变成 N 个，内存与冷启动都翻倍。
- ❌ **先取全局 top-k 再按 scope 筛**：正确切片被其他课堂的片挤掉，**召回确定性下降且不报错**。

✅ **正确做法：全局只建一份 BM25（IDF 稳定、缓存只要一份），
打分后先在候选下标上按 scope 过滤，再取 top-k**：

```python
def _bm25_search(vectorstore, query, k, scopes=None):
    bm25, docs, doc_scopes = _get_bm25_store(vectorstore)   # 第三个返回值：与 docs 对齐的 scope 数组
    if bm25 is None or not docs:
        return []
    tokens = _tokenize(query)
    if not tokens:
        return []
    scores = bm25.get_scores(tokens)
    allowed = None if not scopes else set(scopes)
    order = sorted(
        (i for i in range(len(docs)) if allowed is None or doc_scopes[i] in allowed),
        key=lambda i: scores[i],
        reverse=True,
    )[:k]
    return [docs[i] for i in order if scores[i] > 0]
```

打分本身是 O(N) 的全量计算（不管过滤与否都要算），所以**多这一步过滤不增加计算量**，
只增加一个下标比较。缓存仍然是"collection 名 → 一份索引"，不需要按 scope 拆分。

> ⚠ **固有耦合**：全局 IDF 意味着某个课堂塞进几千片后，会**轻微改变共享库的 BM25 排序**。
> 这属于"单库方案的代价"，不是 bug。缓解是给教师上传设单片数上限并监控 `scope` 分布。
> 多 collection 方案不存在这个耦合——这是两者最实质的差别，也是我在
> `docs/proposals/PROPOSALS.md` §7 之外新增的取舍依据。

##### 3.4 父聚合与去重

- `aggregate_parent_docs`（`retriever.py:509`）按 `parent_id` 去重 → §2.3 的 `source` 前缀已保证唯一，函数本身**零改动**。
- `_dedupe(docs, ("source","start_index"))` → 因 `source` 带前缀，**无需改键**。
  若走"source 不带前缀 + 只加元数据"的路线，这里必须改成 `("scope","source","start_index")`。

##### 3.5 两层 floor 与重排

`relevance_floor` / `per_doc_floor` 作用在重排之后，**与过滤无关，零改动**。
但要注意口径：课堂资料与教材的分数分布不同，共用一套 floor 可能让课堂资料被整批滤掉。
上线后必须用真实问答核对"课堂资料能否稳定进入注入"，不能只看 L1（L1 只测共享库）。

#### 四、写入与迁移设计

##### 4.1 增量脚本（`scripts/update_kb.py`）

现有 `read_library()` 读**全表** metadatas 来比对源文件差异。单库后表里混着课堂资料，
不按 scope 过滤会**把课堂文件当成"已删除的共享文件"**，触发大批 `delete(where={"source": ...})`。
这是第二个静默破坏点。

```python
raw = store.get(include=["metadatas"], where={"scope": "shared"})   # 只读共享层
```

删除时说清 scope：

```python
store._collection.delete(where={"$and": [{"scope": "shared"},
                                        {"source": {"$in": sources}}]})
```

`needs_full_rebuild` 的判据不变（`chunk_params_hash` 比对面仍然只取 `scope=shared` 的片）。

##### 4.2 迁移：给现有 248 片回填 `scope="shared"`

**已实测**：Chroma 1.5.9 的 `collection.update(ids=…, metadatas=…)` 是**合并**语义，
不会覆盖 `parent_text` / `parent_id`（旧版本是整体替换，会毁掉父子检索，务必按版本确认）：

```
update 后 keys = ['parent_id', 'parent_text', 'scope', 'source']
=> 结论：合并（安全）
```

且只传 metadatas → **不重算 embedding**，248 片耗时在 1 秒量级。

脚本骨架 `scripts/backfill_scope.py`：

```python
# 1) 取全库 ids + metadatas；2) 缺 scope 的批量（每批 200）update 成 shared
# 3) 打印回填前后 count、以及 get(where={"scope":"shared"}) 的片数，必须相等
# 4) --dry-run 只报数不写
```

**上线顺序**：先回填 → 再开过滤。反过来会在回填完成前把共享库自己查空。

#### 五、与评测体系的关系（这是本方案能低成本落地的关键）

`eval/fingerprint.py` 的指纹是：

```python
sha256( 排序后的 (source, start_index, page_content) 三元组 )
```

**不含 metadata**。所以：

- ✅ 只加 `scope` 元数据 → **指纹不变、L1 基线可继续用**（`bbe0cdc4` / 248 片）
- ❌ 若给共享文的 `source` 加前缀 → 指纹会变（`source` 参与哈希）→ **必须重刷金标准**
- ⚠ 单库后 `collection_fingerprint()` 会把课堂资料也算进去 → **必须加 scope 过滤**，
  否则 L1 每次对比都被课堂内容搅乱：

```python
def collection_fingerprint(vectorstore, where=None):
    raw = vectorstore.get(where=where)     # 传 {"scope": "shared"}
    ...
```

结论：**共享库 `source` 保持不变**是本设计的硬约束；课堂资料的 `source` 才带前缀。

#### 七、风险清单（按严重度）

1. **静默跨课堂泄漏（最高）**：忘传 `scopes` → 默认 `None` → 不过滤 → 学生看到别班资料，
   **不报错、测试也可能全绿**（因为返回的文档本身合法）。
   缓解：① 端点上强制传参，`None` 只在内部单测里用；② **检索后断言**——
   逐条校验 `doc.metadata["scope"] ∈ 允许集合`，不符直接 `raise`，
   把静默泄漏变成可见异常（这也是主流多租户方案的标准兜底）。
2. **增量脚本误删（高）**：`read_library` 不按 scope 收窄 → 把课堂文件当"已删除的共享文件"删掉。
   缓解：单测覆盖"库里有课堂资料时，共享层增量一个 delete 都不发"。
3. **回填前开过滤（中）**：共享库自己被查空，表现为"知识库命中 0 但库里有 248 片"。
   缓解：回填脚本末尾自校验（`get(where={"scope":"shared"})` 片数 == 回填前总数）。
4. **IDF 耦合（中，固有代价）**：课堂语料变多会轻微改变共享库 BM25 排序。
   缓解：设单片数上限 + 监控 scope 分布；若真成问题，退回多 collection。
5. **floor 口径不适配（中）**：课堂资料分数分布与教材不同，可能被整批滤掉。
   缓解：上线后用真实问答核对注入情况，别只看 L1。
6. **`parent_id` 撞车（中）**：`source` 不前缀化就撞；已由 §2.3 设计规避，但必须单测守住。
7. **旧版本 `update` 覆盖元数据（低但危险）**：本项目 1.5.9 是合并语义，
   换版本要重测，否则回填会毁掉 `parent_text`。

#### 八、结论与建议

**改动是否很大？** 中等偏大：约 180 行改动 + 60 行脚本 + 35~45 例单测，3~5 天量级，
且必须重跑 L1（`gold_index_fingerprint` 需按 scope 收窄后确认仍为 `bbe0cdc4`）。

**现在该不该做？** 不该。当前 20 篇 / 248 片 / 课堂数量极少：
- 多 collection 方案（方案 B）**代码量更小、撤销更干净、无泄漏面**，完全够用；
- 单库方案的全部收益（省掉 collection 爆炸）**只有在课堂数上到几十~上百时才兑现**；
- 而它的成本（静默泄漏面 ×2 处、IDF 耦合、评测要按 scope 收窄）**从第一天就开始付**。

**该做的那一半现在就做**：只加 `scope` 元数据（档①）。
指纹不变、检索不变、零回归，成本半天；等触发条件到了，切档③只需加过滤，
不必重写切片与增量逻辑——**把不可逆的迁移成本前置，把有风险的检索改动后置**。

**触发条件（满足任一即切档③）**：
1. 课堂数 > 20~30（collection 管理、BM25 冷启动、清理逻辑开始成为负担）；
2. 需要"一次检索跨多个课堂"（如教师看多班对比）——多 collection 要 N 次检索再合并；
3. 需要按 scope 做全局统计/巡检（`get(where=...)` 一次拿到，多库要挨个查）。

#### 九、规模实测与架构修正（2026-10-26 12:10 补）

> 上下文：A 明确「预期后面规模会很大」。前八节都是在 20 篇 / 248 片的数据上做的定性设计，
> 本节补上用**目标规模**跑出来的数字，并据此修正架构结论。
> 环境：本机 Chroma 1.5.9 / jieba 0.42.1 / rank_bm25 / 384 维向量，临时基准脚本已删除。

##### 9.1 BM25 的成本随规模线性恶化（这是全案的真正瓶颈）

用与线上同一份 `_tokenize`（jieba + 小写归一）和 `BM25Okapi`，构造每片约 100 token 的语料：

| 切片数 | jieba 分词 | BM25 建索引 | 一次打分 | **冷启动合计** | 常驻内存 |
|---|---|---|---|---|---|
| 5 000 | 7.79 s | 0.19 s | 17 ms | **8.0 s** | 20 MB |
| 20 000 | 19.35 s | 0.77 s | 49 ms | **20.1 s** | 81 MB |
| 50 000 | 46.85 s | 1.86 s | 144 ms | **48.7 s** | 203 MB |

（内存为含语料 token 列表的上界，约 4.2 KB/片；线上 `_BM25_CACHE` 还额外持有 `docs`，
其中每片的 `parent_text` 约 3 KB，两万片再加约 60 MB。）

**读法**：BM25 建索引本身不慢（50k 片只要 1.86 s），**慢的是分词**（46.85 s，占 96%）。
而 `_BM25_CACHE` 是「collection 名 → 一份索引」的整份重建机制 ——
**只要课堂池里任何一篇文档被写入，整份索引就要重建**。

于是纯单库方案在 2 万片时会出现一个致命现象：
**教师上传成功 → 缓存失效 → 下一个学生提问要多等 20 秒**（5 万片时 49 秒）。
本项目 p95 门禁是父子 ≤5 s，这会直接击穿，而且表现为「偶发一次极慢」，
排查时极难归因到「半小时前有位老师传了份讲义」。

##### 9.2 Chroma 带 `where` 的检索路径：不是走图，是扫子集

20 000 片 / 384 维，同一个查询向量，只改过滤条件，各跑 10 次取均值：

| 过滤条件 | 平均耗时 | 返回 |
|---|---|---|
| 不过滤（全库） | **3 ms** | 6 条 |
| `scope=shared`（约 50% 子集） | **147 ms** | 6 条 |
| `$in[shared, classroom:1]`（约 51%） | **171 ms** | 6 条 |
| `$in[shared, 5 个课堂]`（约 55%） | **173 ms** | 6 条 |
| `scope=classroom:7`（约 1%） | **29 ms** | 6 条 |

**关键现象**：不带过滤恒为 3 ms，带过滤后耗时随**过滤子集大小**线性增长
（1% → 29 ms，50% → 147 ms），而不是随结果条数变化。
说明带 `where` 时走的不是 HNSW 图搜索，而是**对满足条件的子集做扫描**。

这条实测推翻了一个常见的想当然：「加了 filter 只是多一层 SQL 条件，检索还是走索引」。
不是。**过滤的代价 = 子集大小 × 单条距离计算**，与库总量成正比。

##### 9.3 架构修正：两库分层，`scope` 只用于课堂池

把 9.2 的结论代进来，纯单库（共享 10 万 + 课堂 10 万塞一个 collection）会在**每次提问**时
扫 20 万条中的 10 万条 —— 按 147 ms / 1 万条外推约 **1.5 s 起步**，且随规模继续恶化。
这等于为了省掉「collection 数量」而牺牲「每一次检索」。

修正为**三个物理集合，职责不同**：

| 集合 | 内容 | 是否加过滤 | 检索路径 | 写入频率 |
|---|---|---|---|---|
| `kb_shared` | 教材（`knowledge/cs/`） | **不加** | HNSW 图搜索，3 ms 量级 | 极低（人工审核后才动） |
| `kb_classroom` | **所有课堂**资料 | 加 `scope` 过滤 | 子集扫描，1% 选择性下 29 ms | 高（教师自由上传） |
| 会话级（内存） | 单次上传件 | 不加（collection 本身隔离） | 纯向量 | 每次上传 |

这么分的收益是**三条同时成立**，而纯单库只能拿到第一条：

1. **collection 数量不随课堂增长**（1 个池装 N 个课堂）——这是 A 想解决的问题，做到了；
2. **共享库检索不被过滤拖慢**（不加 filter，永远走 HNSW）——纯单库做不到；
3. **共享库的 BM25 与评测基线物理隔离**（课堂写入不触发共享索引重建、不改指纹）——
   纯单库做不到，这也顺带消掉了 §3.3 说的 IDF 耦合。

BM25 也随之分成两份：`kb_shared` 一份（随教材变更重建，5 万片 49 s 但一年没几次），
`kb_classroom` 一份（随课堂写入重建，靠**异步预热**吸收，见 9.5）。

##### 9.4 规模档位与推荐架构

| 总切片量 | 推荐架构 | 关键依据 |
|---|---|---|
| < 1 万（当前 248） | 一课一 collection 即可，不必上 scope | 方案 B 代码更少、撤销更干净；本方案收益为零 |
| 1 万 ~ 5 万 | **两库分层**（本章 9.3） | 课堂池过滤扫描 <100 ms；BM25 池化后冷启动 20 s 可异步吸收 |
| 5 万 ~ 20 万 | 两库分层 + **课堂池按学期分池** + BM25 异步预热 | BM25 冷启动 49 s 必须切成「每池 <10 s」 |
| > 20 万 | 向量库换 Qdrant / Milvus；**BM25 外置** ES / Meilisearch | Chroma 过滤走子集扫描、单机内存与单进程重建都不再适用 |

**这张表是本节最重要的一行**：`scope` 方案解决的是「**collection 数量**随租户增长」，
不解决「**数据量**增长」。后者要换引擎，是另一个量级的改造（估 2~3 周，且要重做评测口径）。
所以如果「规模很大」指的是几十万片，现在做 scope 只完成了 40% 的功课。

##### 9.5 成本重估（一次性 + 运行期）

**一次性改动**（相对 §六 上调，因为要包含 BM25 池化与异步预热）：

| 项 | 估时 |
|---|---|

#### 〇、结论先行（30 秒版）

#### 一、需求分类：先问「这份资料给谁看、看多久」

`/upload/teacher`（app.py:2214）现在只有一种行为——建会话级内存库（TTL 1 小时、
进程重启即消失）。但教师上传的真实语义有三种，混在一个接口里迟早出事：

| # | 语义 | 典型例子 | 生命周期 | 可见范围 | 对应落法 |
|---|---|---|---|---|---|
| S1 | **备课素材**（用后即弃） | 明天讲课要引用的论文 | 1 小时会话 | 仅上传者本次 | 现状（方案 A），已够用 |
| S2 | **课堂资料**（长期生效） | 本班讲义、错题集、实验指导 | 跟随 `Classroom` 行 | 本课堂成员 | **方案 B（本文）** |
| S3 | **全局内容**（所有课堂共用） | 优质总结、新知识点补充 | 常驻 | 全平台 | 审核晋升 → `knowledge/cs/` |

**判断依据是「生命周期 + 可见范围」，不是「上传者是不是教师」**（决策台账 D1）。
按角色分库会把同一份课堂资料劈成两半——比如教师传的讲义（S2）和助教整理的
错题集（S2）语义完全相同。

#### 二、放哪里：四个选项的评估

##### 选项 0：会话级内存库（现状，方案 A）——S1 的正解，S2 不够

- 已落地：`_index_upload()`（app.py:308）不传 `persist_directory`，纯内存 Ephemeral，
  不落盘、不进 `chroma_kb`，实测不污染基线（上传前后 `chroma_kb` 始终只有
  `cs_basics`，248 片 / `bbe0cdc4` 不变）。
- **对 S1 完全够用**；对 S2 致命缺陷：1 小时 TTL + 进程重启即消失 + 学生检索不到。
- **结论：保留现状服务 S1，不动。**

##### 选项 1：写进共享库 `cs_basics` ——否决

四个硬伤（`docs/specs/RAG_HANDBOOK.md` §9 已登记，此处只列结论）：

1. **全局泄漏**：某教师传份错题集，所有课堂学生都能检索到；
2. **评测基线当场报废**：L1 金标准绑 `gold_index_fingerprint`（`bbe0cdc4` / 248 片），
   库一写就失效且无法复现，重刷金标准约 4 分钟一轮；
3. **无归属、无审核**：质量不可控；
4. **加容易删难**：`delete(where={"source": ...})` 删得掉，但源文件还在的话下次
   重建会「复活」。
- 共享库的正确定位：**数据源是仓库文件 `knowledge/cs/*.md`，Chroma 只是派生索引**。
  「上传到共享库」= 文件落 md → 审核 → `update_kb.py` 增量 → 热重载。这条链是通的，
  缺的只是审核闸门（待 A 定晋升审批人角色，U3）。

##### 选项 2：课堂级 collection（方案 B）——S2 的正解，本文推荐

`classroom_{id}_docs`，与共享库**并行召回**后合并注入。优点：

- **权限边界是物理的**：学生查别的课堂的 collection 在机制上不可能（比
  scope 过滤「靠应用层每次都正确传参」硬得多——scope 方案的最大风险就是
  漏传 filter 造成静默跨课堂泄漏）；
- **不碰共享库**：L1 金标准与指纹零影响（金标准只测 `cs_basics`）；
- **撤销干净**：删课堂 → 删 collection + 原件目录，一个动作；
- 代码量小（对照 §六改动清单）。

代价：collection 数随课堂数线性增长。**当前课堂数个位数，此代价为零**
（规模切换点见 §七）。

##### 选项 3：单库 + scope 元数据 + pre-filter——规模化后的解，现在不做

完整设计与实测见 `docs/proposals/PROPOSALS.md`（§九已按 2 万片规模实测修正为
「两库分层」）。两条硬实测否决了「现在就做」：

- Chroma 带 `where` 不走 HNSW 而是扫过滤子集（50% 选择性 147ms vs 不过滤 3ms）；
- BM25 冷启动瓶颈在 jieba 分词（20k 片 20.1s），教师上传会击穿 p95 ≤5s 门禁。

**结论：档①（只加 `scope` 元数据 + 回填，0.5 天、指纹不变、零回归）可作为
前置投资与方案 B 并行做；档③（课堂池）等触发条件。**

#### 三、三层资料库总览（方案 B 落地后的完整图景）

| 层 | collection | 事实源（真相在文件/DB，Chroma 是派生） | 可见范围 | 生命周期 | 影响 L1 基线 |
|---|---|---|---|---|---|
| 共享库 | `cs_basics` | `knowledge/cs/*.md`（20 篇） | 全部 | 常驻 | **是**（变更需重刷金标准） |
| **课堂库（新）** | `classroom_{id}_docs` | `backend/classroom_docs/{id}/` 原件 + `classroom_documents` 表 | 本课堂成员 | 跟随 `Classroom` 行 | 否 |
| 会话库 | `student_upload_/teacher_upload_{sid}` | 无（用后即弃，不留存） | 仅本人本次 | 1h TTL / LRU | 否 |

关键口径（沿用手册 §9 的已更正结论）：

- **结课 ≠ 删除**。`Classroom` 模型没有结课字段（`db/models.py:58`），课堂库
  生命周期 = `Classroom` 行的生命周期，只有课堂被真正删除才清理——学生结课后
  回来复习本课讲义是正当需求。将来加「结课」应是 `status=archived`（禁写只读）。
- **写入分层、读取合并**（D2）：写入默认落课堂库，审核通过才晋升共享库；
  读取永远「共享库 + 课堂库」并行召回——只查课堂库会让教师资料顶掉教材，
  学生反而变盲。

#### 四、方案 B 详细设计

##### 4.1 存储：原件落盘 + DB 登记 + 派生索引（三层各司其职）

**这是本设计新增的关键机制**——此前散落各处的讨论只讲了 Chroma collection，
没有回答「课堂库的事实源是什么」。共享库的事实源是 md 文件；课堂库若只有
Chroma 索引而没有原件，**换 embedding 模型、改切片参数、Chroma 升级迁移时
全部不可重建**，等于把派生物当成了真相。

```
backend/
├── classroom_docs/{classroom_id}/          # 原件（事实源）
│   └── {doc_id}_{原文件名}.pdf
├── chroma_classrooms/                      # 派生索引（落盘，与 chroma_kb 同级、物理分开）
│   └── classroom_{id}_docs/                # 一课一 collection
└── classroom_documents                     # MySQL 登记表（ai_classroom 库）
```

`classroom_documents` 表（沿用 `ensure_new_columns` 幂等迁移惯例）：

| 列 | 说明 |
|---|---|
| `id` (PK) | doc_id，兼作文件名前缀 |
| `classroom_id` (FK, CASCADE) | 归属课堂 |
| `teacher_id` | 上传者（审计） |
| `filename` / `stored_path` | 原始名 / 落盘路径 |
| `doc_hash` | 内容 sha256 前 16 位——**同课堂去重依据** |
| `chunk_count` / `file_bytes` | 容量统计 |
| `status` | `active` / `deleted`（软删，物理清理走后台） |
| `created_at` / `deleted_at` | 审计 |

设计要点：

1. **原件与索引分离**：PDF 原件可达 10MB，不进 DB；Chroma 目录
   `chroma_classrooms/` 与 `chroma_kb/` 分开，**运维上一眼可分**，备份/迁移/清理
   互不牵连，也杜绝任何脚本把课堂 collection 误算进共享库指纹。
2. **`doc_hash` 去重**：同课堂重复上传同内容 → 409 返回已有 doc_id（幂等）。
3. **切片策略**：PDF 走现有 `_index_upload` 的 900/150 扁平切片（父子模式是
   md 专属，靠 `##` 小节聚合，PDF 没有 markdown 结构，不要硬套）。
4. **source 前缀化**：课堂片的 `source` 记 `classroom:{id}/{doc_id}_{filename}#p{n}`
   ——即使将来并入 scope 课堂池，`parent_id` / 去重键也不会与共享库或其他课堂撞
   （`docs/proposals/PROPOSALS.md` §2.3 的教训）。共享库 `source` **永远不加前缀**。

##### 4.2 上传接口：`/upload/teacher` 扩一个参数，不开新端点

```python
@app.post("/upload/teacher")
async def upload_teacher_document(
    ...,
    teacher_id: int = Form(...),
    classroom_id: int = Form(...),
    persist: str = Form("session"),   # 新增："session"(默认,现状) | "classroom"(方案B)
):
```

`persist="classroom"` 时的行为（在现有 `_require_teacher` 校验之后）：

1. 校验容量配额（§4.5），超限 413；
2. `doc_hash` 查重，重复 409 幂等返回；
3. 原件落盘 `classroom_docs/{id}/`（沿用现有边读边判大小的临时文件机制，
   校验通过后从临时文件拷入，失败不留垃圾）；
4. `Chroma.from_documents(..., persist_directory="chroma_classrooms")` 建索引
   ——**与 `_index_upload` 的差别只有 persist_directory 一个参数**，抽出共用；
5. DB 登记 `classroom_documents` 行；
6. 失效课堂库句柄缓存（§4.4）。

**默认值 `session` 保证存量调用方行为零变化**——这是零回归的兼容开关。

##### 4.3 检索：第三路注入，MVP 不动 `retrieve_knowledge_docs()`

`/chat` 现状已是两路并行注入（app.py:694~727）：

```python
pdf_docs  = retrieve_pdf_docs(...)    # 学生会话库，纯向量
kb_docs   = retrieve_knowledge_docs(...)  # 共享库，完整链路(向量+BM25+RRF+重排+floor)
rag_context = format_pdf_docs(pdf_docs) + format_knowledge_docs(kb_docs)
source_items = summarize_sources(pdf_docs, "upload") + summarize_sources(kb_docs, "kb")
```

MVP 加第三路：

```python
classroom_docs = retrieve_classroom_docs(classroom_id, query, k=3)  # 新函数，纯向量范式
```

**为什么 MVP 走纯向量而不是完整链路**（这是本设计最重要的取舍）：

| 做法 | 代价 | 收益 |
|---|---|---|
| 完整链路（向量+BM25+RRF+重排+floor） | `retrieve_knowledge_docs` 是单库签名（retriever.py:622），要么调两次各自重排（**重排成本×2**，p95 预算 4.3s/5s 直接击穿），要么改成多库联合检索（大改）；`_BM25_CACHE` 按 collection 名做键，**每课堂首次检索冷启动**；课堂资料分数分布与教材不同，**共用 floor 可能整批滤掉** | 召回质量略高 |
| **纯向量（`retrieve_pdf_docs` 范式，MVP）** | 复用现成函数模式，检索耗时 ms 级 | 课堂资料量小（单课堂通常 <几百片）时纯向量完全够用 |

`retrieve_classroom_docs` 照抄 `retrieve_pdf_docs`（retriever.py:739，含 front_matter
特判与去重），加 `classroom_id` 定位 collection。注入上限 `k=3`，防上下文膨胀。
`summarize_sources(docs, "classroom")`——origin 标签机制现成（retriever.py:544），
SSE 协议零改动（只是 sources 数组多一类 origin 值，前端向后兼容）。

**升级触发条件**（写下来，免得将来拍脑袋）：单课堂片数 > 2000，或实测发现
课堂资料命中率不足，再评估上 BM25 + 重排——届时优先「课后台预建 BM25」而不是
请求时冷启动。

##### 4.4 课堂库句柄管理：吃透「P5 教训」

实测教训（memory 2026-10-26）：Chroma `PersistentClient` 打开过的进程持有内存快照，
**写入后已持有句柄的进程看不到新数据，且不报错**。课堂库写入（教师上传）与
读取（学生 /chat）在同一个服务进程里，必须处理：

- **MVP 方案**：不缓存课堂库句柄，每次 `/chat` 现场
  `PersistentClient(path="chroma_classrooms").get_collection(f"classroom_{id}_docs")`。
  Chroma client 创建是轻操作（实测共享库场景无感知），单课堂 collection 小，
  换来「写入即时可见、零缓存一致性问题」。
- 课堂不存在（新课堂无资料）→ `get_collection` 抛 `NotFoundError` → **静默返回
  空列表**（知识库是增强项，失败必须降级，不许 500——XB-19 同款教训）。
- **验证生效用真实检索，不用 `collection.count()`**（count 读 SQLite 元数据
  永远返回最新值，是已知坑，硬约束 6）。

##### 4.5 生命周期与容量治理

| 事件 | 动作 |
|---|---|
| 课堂被删除 | 删 collection（`delete_collection` 或整目录）+ 删 `classroom_docs/{id}/` + DB 行 CASCADE（沿用 `ClassroomMember`/`Message` 的 `ondelete="CASCADE"` 惯例，`db/models.py:102`） |
| 教师删自己的资料 | 软删 DB 行 + `delete(where={"source": {"$in": [...]}})` 按篇删片（同库批量删用 `$in`，避免 N 次全表扫描）+ 原件留待后台清理 |
| 容量配额（MVP 建议值） | 每课堂 ≤ 20 个文件 / ≤ 200MB；超限 413。**限流已有 10/hour 不变** |
| 结课（将来若做） | `status=archived` → 禁上传、检索保留。**绝不删数据** |

##### 4.6 权限

- **上传**：`_require_teacher()`（app.py:1969，已核实校验 role 而非只查 membership）——现成，复用。
- **检索**：零新增逻辑。`/chat` 的 `ChatRequest` 本来就带 `classroom_id`
  （app.py:616 `_classroom_of()`），且已有 `is_member` 校验（app.py:633）——
  课堂成员问答自动落在本课堂库，非成员连 /chat 都进不来。
  **请求协议零改动**（这是方案 B 相比其他方案最省的一点）。

##### 4.7 评测口径影响（必须写清楚，否则上线后指标会「莫名」漂移）

| 层 | 影响 | 对策 |
|---|---|---|
| L1 检索 | **零**（金标准只测 `cs_basics`，物理隔离） | 上线后复跑一次 `smoke_rag.py --compare` 确认指纹仍 `bbe0cdc4` |
| L3/L4 生成与 e2e | **有**：评测对话若带 classroom_id 且该课堂有资料，会注入课堂内容，sources 口径变化 | 评测脚本固定用「无课堂资料的课堂」（或 classroom_id=None 路径），**把课堂库从评测口径里显式隔离**；另设独立的「课堂资料命中」验收场景 |
| 新增验收场景 | 教师传讲义 → 学生提问 → 断言 sources 含 `origin=classroom` 且正文来自该篇 | 写成单测（mock LLM）+ 一条真实冒烟 |

#### 五、晋升通道：课堂库 → 共享库（S3 的路）

```
教师上传(S2, 课堂库) ──教师点「申请全局收录」──▶ knowledge/inbox/{slug}.md 暂存
                                                    │
                                          人工审核（审批人角色待 A 定, U3）
                                                    ▼
                                    移入 knowledge/cs/{category}/ → update_kb.py 增量
                                                    ▼
                                          POST /admin/reload-kb（热重载,现成）
```

- 转入库时必须**转成 md 并人工整理**（PDF → md 的自动转换质量不可控，不自动化）；
- 审核通过后走的是现成增量链路（0.35s/篇 + 热重载），**这一段不需要写新代码**；
- MVP 可以先只做「下载原件 + 手工入库」，UI/流程后补——**不要为一个还没定审批人
  的流程先写代码**。

#### 七、规模演进路线（不要越级跳档）

| 阶段 | 触发条件 | 架构 |
|---|---|---|
| 现在 | 248 片 / 课堂数个位数 | 一课一 collection（方案 B） |
| 档①（可与 B 并行） | 想前置迁移成本 | 只加 `scope` 元数据 + 回填（0.5 天、指纹不变、零回归） |

增长**；几十万片的解法是换引擎，别把档③说成「规模问题已解决」。
