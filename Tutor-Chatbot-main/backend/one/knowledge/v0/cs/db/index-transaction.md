# 数据库索引与事务

## 一句话结论

索引用 B+ 树等结构加速查询（避免全表扫描），代价是写入变慢、占空间；事务用 ACID 保证「一组操作要么全成要么全败」，靠隔离级别在「一致」与「并发」之间权衡，常见脏读/不可重复读/幻读问题由隔离级别和 MVCC 解决。

## 标准答案

**索引（以 B+ 树为例）**

B+ 树是多路平衡树：非叶子节点只存「键+指针」做导航，所有数据都在叶子节点，叶子之间用链表串起来。优点：矮胖（几层就能存海量数据）、范围查询极快（顺着叶子链表扫）。主键索引（聚簇）叶子直接是整行；二级索引叶子是主键值，回表再查。

**事务的 ACID**

- 原子性（A）：要么全做要么全不做（靠 undo log 回滚）。
- 一致性（C）：事务前后数据满足约束。
- 隔离性（I）：并发事务互不干扰。
- 持久性（D）：提交后不丢（靠 redo log / WAL）。

**隔离级别（由低到高）**

- 读未提交：可能脏读。
- 读已提交（RC）：避免脏读，可能不可重复读。
- 可重复读（RR，MySQL 默认）：避免不可重复读，靠 MVCC 快照；幻读用间隙锁（next-key lock）防。
- 串行化：完全隔离，性能差。

## 原理展开

**什么是回表**

用二级索引查到主键值后，还要拿主键去聚簇索引再查一次整行，这第二次查询叫「回表」。如果查询的列都在二级索引里（覆盖索引），就不需要回表，能明显提速。

**MVCC 怎么实现可重复读**

每行数据有隐藏的事务版本号，读操作根据自己事务的快照版本去读「对自己可见」的版本，不阻塞写、写也不阻塞读。这就是「快照读」，是 RR 级别下能重复读、且并发高的原因。

**为什么索引不是越多越好**

每个索引都要在写入时同步更新（增删改都要维护 B+ 树），索引越多写越慢、越占空间；优化器选错索引也会拖慢查询。所以要「按高频查询建索引、避免冗余、留意区分度低的列」。

## 面试常问

1. 为什么用 B+ 树不用哈希/二叉树？哈希不支持范围查询；二叉树太高（磁盘 IO 多）；B+ 树矮胖、叶子链表让范围查询很快，且更适合磁盘（一次 IO 读一页）。
2. 什么是覆盖索引？查询所需的列都在索引里，不用回表，显著提速。
3. 幻读是什么、怎么防？同一事务两次范围查询，第二次多出了新插入的行。RR 下用间隙锁（锁住范围之间的空隙）防止别的事务插入，从而防幻读。
